# Kiko Workbench 插件开发规范

> 面向外部开发者 / Agent：从零设计、开发、构建一个插件，并集成到 Kiko Workbench 工作台。
> 本规范与当前实现一一对应，所有接口均以 `packages/plugin-sdk` 实际导出为准。
> 参考实现：`packages/plugins/file`（文件读写）、`packages/plugins/document`（docx 生成）、`packages/plugins/dev`（长任务/取消/进度、声明式配置、微应用推送）。

---

## 1. 架构模型：先建立正确的心智图

```
┌─────────────────────────────────────────────┐
│  Electron 主进程                             │
│  ┌────────────┐  ┌──────────────────────┐    │
│  │ Registry   │  │ ExecutionRuntime     │    │
│  │ (读清单注册)│  │ (每插件独立子进程,    │    │
│  └────────────┘  │  懒启动/崩溃重启)     │    │
│                  └─────────┬────────────┘    │
└────────────────────────────┼────────────────┘
                             │ 消息协议(HostCommand/HostEvent)
                 ┌───────────▼───────────┐
                 │ 插件进程(utilityProcess)│
                 │  host-entry → 你的代码 │
                 │  KikoPlugin 对象       │
                 └───────────────────────┘
```

三条铁律：

1. **一个插件 = 一个独立子进程**。你的代码崩溃不会拖垮工作台；连续崩溃 3 次会被熔断（插件显示"异常"，用户可重新启用）。
2. **插件只面对 `@kiko-workbench/plugin-sdk`**。禁止 import `electron`、`@kiko-workbench/core`——依赖方向不可倒置。
3. **主进程不加载你的 JS**。启动时只读 `manifest.json` + `capabilities.json`（纯数据注册）；你的代码在首次被调用时才加载执行（懒启动）。

## 2. 快速开始：最小插件的五个文件

### 2.0 第 0 步：获取 SDK

`@kiko-workbench/plugin-sdk` 与 `@kiko-workbench/protocol` **未发布公共 npm**（registry 必 404）。工作台内置 **sdk 分发插件**落盘了全套 SDK 物料（vendor 目录），开发插件前先从工作台获取：

| 场景 | vendor 物料根目录（`sdk_root`） |
|---|---|
| 开发态（源码运行） | `<repo>/packages/plugins/sdk/vendor/@kiko-workbench/` |
| 安装版 | `<安装目录>/resources/plugins/sdk/vendor/@kiko-workbench/` |

不确定路径时让 Agent 调 `sdk.install_guide`（返回 `sdk_root` + 部署目标 `user_plugins_root` + 双轨指引）；`sdk.manifest` 可校验物料版本与文件清单。

获取 SDK 有**两条轨道**（`sdk.install_guide` 的 `mode` 字段区分）：

- **agent 轨（缺省，零 shell）**：无终端的 Agent 走这条——不需要 npm install、不需要终端、不需要重启工作台。五步全程 WS 能力调用：`file.write` 五件套源码（SDK 依赖无需安装，`sdk.build` 构建时经 alias 表从 vendor 物料直接内联）→ `sdk.build` → `sdk.deploy` → `plugins.rescan`（部署后重扫，本轮 discover 即可见）→ discover / describe / invoke 验证。
- **human 轨（`mode: "human"`）**：有终端的开发者走这条——可引第三方库、可跑 tsc 类型检查。完整 8 步指引含 npm 命令，流程见下。

> **Agent 读不到本地文档时**：本规范随 SDK 物料一并落盘在 vendor 目录，可调 `invoke("sdk.spec")` 获取全文（或传 `section` 参数按章节拉取，控制上下文占用）——`install_guide` 响应的 `spec_read_via` 字段会给出此指引。

human 轨安装命令（**实测定稿形态，逐字符照用**）：

```bash
npm install --install-links "<sdk_root>/plugin-sdk" "<sdk_root>/protocol"
```

两个不可省的细节：

1. **两包同一条命令**：npm 才能把 plugin-sdk 对 protocol 的依赖去重为本地目录；分开安装会让 npm 去 registry 搜索而 404。
2. **`--install-links` 必须携带**：npm 对目录源默认创建符号链接（junction）而非复制——esbuild 解析符号链接为真实路径后将从 vendor 目录向上找不到 `@kiko-workbench/protocol`，bundle 直接报 `Could not resolve`。该开关强制复制到 `node_modules`，tsc 与 esbuild 均正常解析。

SDK 就位后，一个最小插件只需五个文件（前四个手写，`dist/` 构建产出）：

```
my-plugin/
├── manifest.json        # 插件身份
├── capabilities.json    # 能力清单（对外契约）
├── dist/index.js        # 构建产物（bundle 后的单文件，entry 指向它）
├── src/index.ts         # 源码（TypeScript 推荐）
└── package.json         # 仅开发期需要
```

**manifest.json**

```json
{
  "id": "my-plugin",
  "name": "My Plugin",
  "description": "一句话描述（UI 插件卡片展示）",
  "version": "1.0.0",
  "entry": "dist/index.js",
  "permissions": []
}
```

**capabilities.json**

```json
[
  {
    "id": "my-plugin.echo",
    "name": "Echo",
    "description": "原样返回输入的消息文本",
    "input_schema": {
      "type": "object",
      "properties": {
        "message": { "type": "string", "description": "要回显的文本" }
      },
      "required": ["message"]
    },
    "output_schema": {
      "type": "object",
      "properties": {
        "message": { "type": "string" }
      },
      "required": ["message"]
    },
    "examples": [
      { "input": { "message": "你好" }, "output": { "message": "你好" } }
    ]
  }
]
```

**src/index.ts**

```typescript
import {
  ERROR_CODES,
  RpcError,
  type KikoPlugin,
  type PluginContext,
  type InvocationContext,
} from "@kiko-workbench/plugin-sdk";

export function createMyPlugin(): KikoPlugin {
  let pluginCtx: PluginContext | undefined;

  return {
    async setup(ctx: PluginContext): Promise<void> {
      pluginCtx = ctx; // 保存沙箱基座（读写文件时用，纯计算插件可不用）
    },

    async handle(capabilityId: string, input: unknown, ctx: InvocationContext): Promise<unknown> {
      if (capabilityId !== "my-plugin.echo") {
        throw new RpcError(ERROR_CODES.PLUGIN_EXECUTION_ERROR, `不支持能力：${capabilityId}`);
      }
      const { message } = input as { message: string };
      ctx.log(`echo: ${message}`); // 写执行日志（Log，区别于 Event）
      return { message };
    },
  };
}

// host 经 manifest.entry 动态加载 default 导出（必须有这一行）
export default createMyPlugin();
```

**构建（关键步骤，不可跳过）**

> **agent 轨无需自己做这一步**：`sdk.build` 代劳——工作台内 utilityProcess 直接 spawn esbuild，SDK 依赖经 alias 表从 vendor 物料内联，产物同样自包含。human 轨手工执行以下命令：

```bash
npx esbuild src/index.ts --bundle --format=esm --platform=node --target=node22 --outfile=dist/index.js
```

> 为什么必须 bundle：插件目录（`resources/plugins/`）旁没有 `node_modules`。产物必须是**零外部 import 的自包含单文件**（除 Node 内置模块外，`@kiko-workbench/plugin-sdk` 及任何第三方依赖都要 inline 进去）。`sdk.build` 的自包含校验与此同口径（产物含裸包名 import → 50001）。

## 3. manifest.json 字段规范

| 字段 | 类型 | 必填 | 校验规则（Registry 启动时执行） |
|---|---|---|---|
| `id` | string | 是 | 非空；即插件目录名约定与 UI 展示标识 |
| `name` | string | 是 | 非空；UI 插件卡片名称 |
| `description` | string | 否 | 缺省空串；UI 卡片描述 |
| `version` | string | 是 | 非空；建议 semver |
| `entry` | string | 否 | 缺省 `"index.js"`；相对插件目录的 JS 入口 |
| `permissions` | string[] | 否 | 缺省 `[]`；声明式权限（如 `"filesystem.read"`），当前版本仅作展示与记录 |

校验失败 → 插件置 **error 状态**（UI 显示原因），不影响其他插件加载。

---

## 4. capabilities.json 字段规范

文件必须是 `CapabilityDefinition[]` 数组，每个元素：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | **全局唯一**（跨插件冲突 → 整个插件拒绝注册）。命名约定：`<plugin-id>.<action>`，如 `file.write`、`document.create` |
| `name` | string | 是 | 能力短名（Agent 发现用） |
| `description` | string | 是 | 给 Agent 看的功能描述，写清楚输入输出语义，越准确被选用越准 |
| `input_schema` | JSON Schema (draft-07) | 是 | invoke 时主进程 ajv 校验，不通过返回 40002（data 携带明细） |
| `output_schema` | JSON Schema (draft-07) | 是 | 输出契约（文档性约束 + Agent 消费依据） |
| `examples` | `{input, output}[]` | 否 | describe 时返回，强烈建议提供（Agent 理解用法的最佳途径） |
| `timeout_ms` | number | 否 | 执行超时毫秒数，缺省 **30000**；超时返回 40006 |

要点：

- `discover` 响应**不含 schema**（只有 id/name/description/plugin），Agent 要看 schema 需调 `describe(capability_id)` —— 所以 `description` 是唯一的发现期卖点，认真写。
- input 顶层必须是 object（协议约定：params 仅对象，无批量请求）。
- schema 是运行时强校验（40002），不是文档装饰——定义错了调用方会被拦。

## 5. 插件接口（KikoPlugin）

```typescript
interface KikoPlugin {
  setup?(ctx: PluginContext): Promise<void>;      // load 后一次
  handle(capabilityId: string, input: unknown, ctx: InvocationContext): Promise<unknown>;
  teardown?(): Promise<void>;                      // 进程回收前（尽力而为）
}
```

导出方式：**`export default <KikoPlugin 实例>`**。ESM default 与 CJS `module.exports` 均兼容（host 动态 import 后取 `.default ?? 模块本身`）。缺 `handle` 函数 → 加载失败（error 状态）。

- `setup` 抛错 → 插件进入 error（不装载）。
- `teardown` 失败不影响进程回收（只有清理机会，无保证）。

### 5.1 PluginContext（setup 注入）

| 字段 | 说明 |
|---|---|
| `pluginId` | 本插件 id |
| `workspaceRoot` | 工作空间根目录；本插件产物目录约定为 `workspace/<plugin_id>/` |
| `documentsDir` | 系统文档目录（读取沙箱基座） |
| `userPluginsRoot` | 第三方插件根目录（`%APPDATA%/…/plugins`；sdk 类插件部署指引用） |
| `esbuildBinaryPath` | esbuild CLI 二进制绝对路径（宿主注入，免 npm install 即可构建） |
| `config` | 插件配置值（§5.3）：已保存值合并 schema default；未声明配置的插件注入 `{}` |
| `ui` | 微应用消息通道（§5.4）：`ui.send(payload)` 向本插件前端窗口单向下发；未声明 `contributes.ui` 时调用恒拒 40010（接口形状稳定） |

### 5.2 InvocationContext（handle 每次注入）

```typescript
interface InvocationContext {
  progress(percent: number, message?: string): void;  // 0-100，触发 execution.progress 事件
  log(message: string): void;                          // 执行日志（与事件分离，UI Trace 展示）
  isCancelled(): boolean;                              // 协作取消检查点
  artifacts: {
    save(filename: string, data: Buffer | string, mime_type?: string): Promise<ArtifactInfo>;
    register(file: string, filename: string, mime_type: string, size: number): void;
  };
  ui: {
    send(payload: unknown): Promise<void>;             // 微应用推送（§5.4；与 PluginContext.ui 同一通道）
  };
}
```

### 5.3 插件配置（ctx.config，声明式）

插件需要用户配置（API Key、偏好开关等）时，**不要自己读配置文件**——在 manifest 声明结构，宿主统一存储、校验、渲染设置表单，加载时经 `ctx.config` 注入。插件代码只读配置、永不接触配置 UI，秘密不过 Agent 手。

**声明**（manifest.json，完整样例见 `packages/plugins/dev/`）：

```json
"contributes": {
  "configuration": {
    "type": "object",
    "properties": {
      "api_key": {
        "type": "string", "title": "API Key",
        "description": "在 openweather.com 控制台获取",
        "x-kiko-secret": true
      },
      "unit": {
        "type": "string", "enum": ["celsius", "fahrenheit"],
        "default": "celsius", "title": "温度单位"
      },
      "timeout_ms": { "type": "number", "default": 10000, "minimum": 1000, "title": "请求超时（毫秒）" },
      "auto_refresh": { "type": "boolean", "default": false, "title": "启用自动刷新" }
    },
    "required": ["api_key"]
  }
}
```

**v1 支持的 schema 子集**（超出即注册期拒绝，插件置 error 态）：

| 类型 | 表单控件 | 附加约束 |
|---|---|---|
| `string` | 文本输入（`x-kiko-secret: true` → 密码型遮蔽） | `enum` → 下拉选择 |
| `number` / `integer` | 数字输入 | `minimum` / `maximum` 前端提示 |
| `boolean` | 开关 | — |

不支持（v1）：`array`、嵌套 object、`oneOf`/`anyOf`/`allOf`。扩展关键字走 `x-kiko-` 前缀（JSON Schema 规范保留的供应商扩展位）。

**消费**（插件侧只读）：

```typescript
async setup(ctx: PluginContext) {
  this.config = ctx.config;  // load 期一次性快照
}

async handle(capabilityId, input, ctx) {
  // 关键配置缺失 → 结构化错误 + 指引（Agent 转达即闭环）
  if (typeof this.config.api_key !== "string" || this.config.api_key === "") {
    throw new RpcError(ERROR_CODES.PLUGIN_EXECUTION_ERROR,
      "api_key 未配置：请在工作台插件面板点击「设置」填写（保存后下次调用生效）");
  }
  // 非关键配置 → 缺省兜底（类型防御回落，配置损坏不崩溃）
  const unit = this.config.unit === "fahrenheit" ? "fahrenheit" : "celsius";
}
```

**语义要点**：

- **required 是表单完整性约束，不是运行时前置条件**——宿主不拦截调用。缺关键配置时插件在 handle 中抛含"请到设置面板配置"指引的结构化错误；非关键配置缺省兜底照常运行（两种模式的活样例见 dev 插件 `dev.greeting`）。
- **生命周期**：配置存于 `userData/plugin-config/<pluginId>.json`，与插件目录解耦——卸载不删（同 id 重装自动恢复）、导出 zip 不含（secret 不外泄）。
- **未知字段透传**：schema 已删除/改名的旧字段原样保留注入——这是插件做配置结构迁移的数据来源。
- **生效时机**：保存后宿主终止运行中的插件进程，懒启动机制在下次调用自动重载新配置。
- **秘密纪律**：`x-kiko-secret` 字段值**不得**出现在返回值、`ctx.log` 日志、错误信息、产物内容中（调用日志与对话上下文均可见）；表单侧已遮蔽展示。
- **v1 明文存储**：配置文件为明文 JSON（本地单用户场景）；safeStorage 加密列为 v2 候选。

### 5.4 微应用（contributes.ui + ctx.ui.send）

插件需要自己的前端界面（仪表盘、状态监视、数字人展示等）时，**不要内嵌 WebView / 弹自己的 BrowserWindow / 起本地 HTTP 服务器**——在 manifest 声明一份前端资产，宿主统一开窗、统一服务、统一桥接。一个微应用插件 = 一份前端资产 + 一条单向桥 + 一个独立窗口（v1 仅独立窗口；内嵌面板/卡片留 v2）。

**声明**（manifest.json；完整样例见 `packages/plugins/dev/web/`）：

```json
"contributes": {
  "ui": { "entry": "web/index.html" }
}
```

`entry` 为相对插件目录的 HTML 入口路径。注册期校验（失败 → 插件 error 态）：

- 非空字符串、相对路径分段安全（拒绝绝对路径 / `..` / 盘符 / 反斜杠混用）
- 文件存在且为常规文件（前端资产必须随插件目录分发）

**前端资产布局**（`web/` 目录，纯静态文件，不参与 esbuild bundle）：

```
web/
├── index.html    # 入口页面
├── app.css       # 样式（可选）
└── app.js        # 脚本（必须外链文件——见下方 CSP 约束）
```

**运行机制**（宿主承担，插件零窗口代码）：

- 加载：用户点击插件卡片「打开界面」→ 宿主开沙箱窗口，经自定义协议 `kiko-plugin://<pluginId>/` 加载你的 `web/` 资产。不同插件不同源（A 插件的页面拿不到 B 插件的 DOM / localStorage）。
- 单实例：同一插件窗口仅一个——再次点击「打开界面」聚焦既有窗口而非新开。
- 安全：窗口 `contextIsolation` 开启、`nodeIntegration` 关闭；宿主对 HTML 响应注入 CSP（`script-src 'self' 'wasm-unsafe-eval'`——禁内联脚本与远程加载、放行 WebAssembly 编译（Live2D Cubism 5 等 wasm 运行时可用）；`connect-src 'self'`——仅许 fetch 本插件目录内的静态资产（.wasm / 模型文件等），**外部网络出口全禁**——动态数据流只经宿主桥，不经 fetch）。**前端代码不得引用任何 CDN / 远程资源。**
- 生命周期：窗口开着期间插件后端进程不被 idle 回收（UI 租约）；窗口关闭后恢复常规回收。

**桥契约**（前端侧，`window.kikoPluginUi` 由宿主 preload 注入）：

```javascript
// v1 仅单向下发订阅：后端 ctx.ui.send(payload) → 前端 listener(payload)
const off = window.kikoPluginUi.onMessage((payload) => {
  // 渲染推送内容（payload 形状由你的后端定义）
});
```

**后端推送**（`ctx.ui.send`，`PluginContext.ui` 与 `InvocationContext.ui` 为同一通道）：

```typescript
async handle(capabilityId, input, ctx) {
  const payload = { kind: "tick", value: 42, at: new Date().toISOString() };
  try {
    await ctx.ui.send(payload);   // resolve = 宿主已投递到窗口
  } catch (e) {
    // 窗口未开（用户没点「打开界面」/ 已关闭）→ 40010
    if (e instanceof RpcError && e.code === ERROR_CODES.PLUGIN_UI_NOT_OPEN) {
      throw new RpcError(ERROR_CODES.PLUGIN_UI_NOT_OPEN,
        "插件界面未打开：请先在工作台插件面板点击「打开界面」");
    }
    throw e;   // 其余异常原样透传（不吞不包装）
  }
  return { delivered: true };
}
```

**语义要点**：

- **v1 单向**：仅后端 → 前端下发。前端 → 后端的事件上报（用户在 UI 里直接操作）留 v2——届时桥扩 `request` 方法，前端资产不用改结构。
- **Agent 不碰窗口**：Agent 全程不 spawn / focus / 控制窗口——用户开、用户关。表面未开时能力返回结构化错误（如上例），Agent 转达即闭环；headless / autopilot 宿主下行为一致（恒 40010）。
- **resolve ≠ 已渲染**：`ui.send` resolve 仅代表宿主已投递到窗口，不代表前端已执行渲染。订阅建立前（页面加载竞态窗口内）发送的消息不重放——推送时机应在窗口打开之后的稳态。
- **payload 限制**：结构化克隆安全的值（JSON 形状）；循环引用等异常值会被宿主拒绝。
- **超时兜底**：宿主 10s 内未回执 → reject（插件侧无需自设超时）。
- 参考实现：dev 插件 `dev.uitest` 能力（推送 + 40010 指引 + 异常透传三极）+ `web/` 消息流页面。

## 6. 沙箱与产物（涉及文件操作必读）

### 6.1 路径安全：resolveSafe

所有文件操作的路径**必须**经 SDK 的 `resolveSafe(base, target)` 校验，插件自身不得手工拼接/放行路径：

```typescript
import { resolveSafe } from "@kiko-workbench/plugin-sdk";

// 读：以 documentsDir 为基座（file.read / file.list 同款语义）
const file = resolveSafe(pluginCtx.documentsDir, input.path);   // 越界抛 50001

// 写：以 workspaceRoot 为基座
const target = resolveSafe(pluginCtx.workspaceRoot, input.path);
```

`resolveSafe` 拒绝：`..` 注入、绝对路径越界、任何落在 base 之外的目标。校验失败抛 `RpcError(50001)`，会作为该次调用失败返回给调用方。

### 6.2 产物落盘：唯一合法入口

插件生成文件（报告、图片、docx……）**必须**走 `ctx.artifacts`，产物才会被登记进工作台的产物表（UI 可见、"打开所在文件夹"可用）：

- `artifacts.save(filename, data, mime_type?)` —— 推荐入口。自动落盘到 `workspace/<plugin_id>/`，**同名自动追加序号**（`报告.docx` → `报告 (2).docx`，永不静默覆盖），返回 `ArtifactInfo`：

```typescript
interface ArtifactInfo {
  file: string;          // 绝对路径
  relative_path: string; // 工作空间相对路径（正斜杠）
  filename: string;      // 实际落盘名（冲突时含序号）
  mime_type: string;
  size: number;          // 字节数
}
```

  - `filename` 仅允许纯文件名（含 `/`、`\`、`..` → 50001 拒绝）。

- `artifacts.register(file, filename, mime_type, size)` —— 仅当你要实现"显式路径覆盖语义"（如 file.write：路径即意图）时自行写盘后登记，不自动改名。

## 7. 错误处理

统一用 SDK 的 `RpcError`，错误码与协议 5.5 一一对应（勿自造数值）：

| code | 常量 | 场景 |
|---|---|---|
| 40005 | `PLUGIN_UNAVAILABLE` | 插件未初始化（setup 未跑）等 |
| 50001 | `PLUGIN_EXECUTION_ERROR` | **插件业务错误默认码**：IO 失败、路径越界、输入防御复检不通过等 |
| 40006 | `EXECUTION_TIMEOUT` | （主进程侧触发，插件不抛）超时 |
| 40007 | `EXECUTION_CANCELLED` | （host 侧触发，插件不抛）取消 |

约定：

```typescript
import { ERROR_CODES, RpcError } from "@kiko-workbench/plugin-sdk";

// 抛 RpcError → code/message 原样透传给调用方
throw new RpcError(ERROR_CODES.PLUGIN_EXECUTION_ERROR, `生成文档失败：${e.message}`);

// 抛普通 Error/异常 → 统一包装为 50001（message 保留）
```

## 8. 长任务：进度、取消、超时

长任务（秒级以上）必须实现协作取消，参考 `packages/plugins/dev`（`dev.longtask` 能力）的分段循环模式：

```typescript
const STEP_MS = 100; // 检查点步长（取消响应延迟上限 ≈ 步长）
const start = Date.now();

for (;;) {
  const remain = durationMs - (Date.now() - start);
  if (remain <= 0) break;
  await sleep(Math.min(STEP_MS, remain));   // 分段 sleep，不阻塞事件循环

  if (ctx.isCancelled()) {
    // 抛错即可，host 按 cancelled(40007) 上报
    throw new RpcError(ERROR_CODES.EXECUTION_CANCELLED, "已取消");
  }
  // 周期进度（0-100）
  ctx.progress(Math.round((elapsed / durationMs) * 100), `已处理 ${elapsed}ms`);
}
```

三条红线：

1. **绝不 `while(true)` 无检查点死循环**——取消只对协作插件温和；不协作插件会被主进程 5 秒宽限后**强杀**（进程销毁，状态记 cancelled，但清理代码不执行）。
2. **单步同步计算不要超过几百毫秒**——`handle` 里长阻塞会卡住取消检查点与进程命令通道。
3. 预计超过 30s 的能力，在 capabilities.json 显式设 `timeout_ms`（超时=失败 40006，不可恢复）。

## 9. 依赖与构建约束

| 允许 | 禁止 |
|---|---|
| `node:*` 内置模块（fs/path/crypto/child_process…） | `import "electron"` |
| `@kiko-workbench/plugin-sdk`（bundle 进产物） | `import "@kiko-workbench/core"` / 任何 core 内部模块 |
| 第三方 npm 库（必须 bundle inline） | 运行时依赖插件目录外的 node_modules（不存在解析链） |

构建命令（esbuild，与内置插件打包链同构）：

```bash
npx esbuild src/index.ts --bundle --format=esm --platform=node --target=node22 --outfile=dist/index.js
```

- 运行时是 Electron 内嵌 Node 22（utilityProcess），`--target=node22`。
- 产物单文件；检查方式：`dist/index.js` 里不应残留裸包名 import（Node 内置 `node:` 前缀除外）。
- Native 模块（.node 二进制）**不可用**——utilityProcess 与 asar 环境下无编译/加载保障（全工程零原生依赖约束）。

## 10. 集成到工作台

工作台扫描**两个**插件根目录（内置在前，注册优先级更高）：

| 场景 | 位置 | 说明 |
|---|---|---|
| 开发态（源码运行 `pnpm dev`） | `<repo>/packages/plugins/<your-plugin>/` | 内置根 |
| 安装版·内置插件 | `<安装目录>/resources/plugins/<your-plugin>/` | 随安装包分发，升级时整体替换 |
| **安装版·第三方插件（推荐）** | `%APPDATA%/kiko-workbench-desktop/plugins/<your-plugin>/` | **用户目录，覆盖安装不丢失**——放安装目录会被升级清空，且 Program Files 下无写权限 |
| 环境变量覆盖（测试用） | `KIKO_PLUGINS_ROOT=<dir>`（内置根）/ `KIKO_USER_PLUGINS_ROOT=<dir>`（第三方根） | 启动注入 |

**第三方插件必须放 userData 的 plugins 目录**（上表第三行），理由：

1. NSIS 覆盖安装会清空安装目录 `resources` 下的非安装清单文件；
2. `perMachine` 安装到 Program Files 时普通用户对 `resources` 只读；
3. 内置插件随版本演进、第三方插件归用户所有，生命周期本就不同。

冲突规则：第三方插件 **id 与内置插件相同时内置优先**（第三方不注册，日志告警）；capability id 与任何已注册能力冲突时该插件整体置 error。

放置与生效方式**按轨道二选一**：

- **agent 轨（零重启）**：`sdk.deploy` 把三件套（manifest / capabilities / dist/index.js）复制到 `user_plugins_root/<id>`，随后调 `plugins.rescan`——本轮 `discover` 即可见新能力，无需重启工作台。
- **human 轨**：手工把插件目录放入上表位置后**重启应用**（Registry 仅启动时扫描）。

验证链路（双轨一致）：

1. UI 插件卡片出现、状态"运行中"（若"异常"→ 悬停/展开看 error_reason：manifest 解析失败、capability id 冲突、entry 缺 default 导出是三大常见原因）。
2. `discover` 看到你的能力（仅 enabled 插件）。
3. `describe` 拿到 schema/examples。
4. `invoke`（sync 短任务 / async+轮询长任务）实测。

WS/HTTP 冒烟（token 见 `settings.json` 的 `access_token`）：

```bash
# HTTP 通道（Bearer 鉴权，sync 方法可用）
curl -s -X POST http://127.0.0.1:47830/rpc \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"discover","params":{}}'
```

## 附：能力调用方视角（你的能力如何被使用）

调用方（Agent / UI）通过 JSON-RPC 调用你的能力，完整链路：

```
invoke(capability_id, input, mode)
  → 主进程 ajv 校验 input_schema（不通过 40002）
  → 插件进程 handle(capabilityId, input, ctx)
  → 返回值作为 result.data；artifacts 登记 → 响应 result.artifacts
  → 事件流：execution.started / progress / log / completed|failed|cancelled
```

你写的 `input_schema` 就是调用方的入参契约，`handle` 返回值就是 `result.data`——schema 与实现不一致时，Agent 会被 schema 误导，务必保持同步。

## 附：插件自管数据存储（按 workload 选型）

插件在运行中积累自有数据（日志、事件流、采集记录）时，按数据形态选存储方案——**崩溃根源是"整文件读改写"访问模式，不是 JSON 格式本身**：

| Workload 形态 | 选型 | 适用量级 |
|---|---|---|
| 偶写 + 小数据（状态缓存、小配置） | 整文件 JSON（读改写） | < 千条；全量重写成本可忽略 |
| 频繁追加 + 查询（日志、事件流、采集记录） | **JSONL 追加日志**（约定见下） | 数万至数十万条；追加 O(1)，流式查询内存恒定 |
| 高频更新/删除 + 条件检索/聚合 | SQLite 预案（未实施，见文末） | 差距是数量级的（100–1000 倍） |
| 产物型输出（报表、导出文件） | artifacts 管道（§6.2） | 非本附录议题 |

**核心判据**：记录条数本身不是开关，**"条数 × 写频率 × 是否高频更新删除"** 才是。只追加不删除的场景 JSONL 兜得住；出现"把第 3 万条的状态改成 X"类 workload 时——不要手工实现"重写去行"，那是 SQLite 预案的触发信号。

### JSONL 写法约定（零平台代码，插件自助遵守）

- **路径**：`<workspaceRoot>/<plugin_id>/data/<name>.jsonl`（`workspaceRoot` 已由 PluginContext 注入；`data/` 子目录与产物文件隔离）。生命周期与配置一致：插件卸载不清理，同 id 重装自动恢复。
- **行格式**：每行一个 UTF-8 JSON 对象，`\n` 结尾；禁止跨行 JSON、禁止空行。首行可保留为元数据行（如 `{"_meta": true, "version": 1}`）供迁移判别。
- **追加写入**：`fs.appendFile` 或 `createWriteStream({ flags: "a" })`——**只追加，永不整文件重写**。
- **读取查询**：`readline` 逐行流式解析，**禁止 `readFile` + 整体 `JSON.parse`**（即崩溃访问模式）。热路径可在 setup 时建内存索引（Map），增量维护。
- **轮转**：单文件建议上限 10 MB，超出后 `rename` 为 `<name>.<yyyyMMddHHmmss>.jsonl`，保留最近 5 代，最老代删除。
- **边界**：需要**更新/删除**语义时，即为触发 SQLite 预案的信号。

### SQLite 预案（已设计，未实施）

触发条件（三者同时满足）：记录量 > 10 万条；存在高频更新/删除操作；存在按条件检索/聚合的查询需求。形态：manifest 声明 `contributes.database: true` → 宿主注入 `ctx.databasePath`（`plugin-data/<pluginId>.db`）→ 插件进程内 `node:sqlite` 自开自管（WAL + `busy_timeout` + `PRAGMA user_version` 迁移）。满足触发条件时向平台方申请启用，不要自行引入其他数据库依赖。
